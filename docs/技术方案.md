### 模块间依赖规则
- `crm-admin` 依赖所有业务模块
- 业务模块（system/market/customer/business/service/report）互相之间**不直接依赖**
- 业务模块都依赖 `crm-common`
- 跨模块调用通过 `crm-admin` 的 facade 或事件总线，避免循环依赖

## 四、关键设计

### 4.1 鉴权流程
1. 登录：`POST /auth/login` → 校验密码 → 生成 JWT（含 userId、deptId、roles）
2. 前端将 token 存 localStorage，axios 拦截器塞入 `Authorization: Bearer xxx`
3. 后端 `JwtAuthenticationFilter` 解析 token，写入 SecurityContext
4. 接口加 `@PreAuthorize("hasAuthority('customer:add')")` 控制权限

### 4.2 数据权限
基于 `sys_role.data_scope` 实现，详见 4.6 节。

### 4.3 线索分配与抢单
- 线索入库 → `market_clue`（status=0 待分配）
- 规则引擎按 区域/行业/销售能力 计算目标销售（`ClueAssignRuleService`）
- 调用企业微信 API 推送消息（1 分钟内）
- 异常兜底：分配失败 → 进入待分配池，管理员手动处理
- 抢单：`claimClue` 使用条件更新 `WHERE status=0` 实现乐观锁，防并发竞态

### 4.4 公海池回收
Spring 定时任务 `CustomerPoolTask`（每日 02:00）扫描 `cus_customer`：
```sql
WHERE in_pool = 0
  AND owner_id IS NOT NULL
  AND (last_follow_time < NOW() - INTERVAL 30 DAY
       OR (last_follow_time IS NULL AND create_time < NOW() - INTERVAL 30 DAY))
```
批量 `UPDATE ... SET in_pool=1, owner_id=NULL`；公海池通过 `cus_customer.in_pool` 字段实现，无独立表。

### 4.5 跟进提醒与商机预警
- `FollowRemindTask`（每日 09:00）：扫描 `cus_follow_record.next_follow_time` 落在今日的记录，按数据权限过滤后写入 `sys_message` 推送。
- `OpportunityStagnantTask`（每日 09:00）：扫描 `bus_opportunity.stage_change_time` 超过 15 天未推进的商机，推送预警消息。

### 4.6 数据权限
基于 `sys_role.data_scope`，由 `DataPermissionService.getVisibleOwnerIds()` 返回当前用户可见的 owner_id 列表：
- 本人（data_scope=1）：`[当前用户ID]`
- 本部门（data_scope=2）：本部门全部用户 ID
- 本部门及下（data_scope=3）：递归子部门用户 ID
- 全部（data_scope=4）：返回 null（不过滤）

业务查询时通过 `wrapper.in(xxx::getOwnerId, visibleOwnerIds)` 拼接 IN 条件。

### 4.7 编号生成（防碰撞）
- 合同编号：`HT-yyyyMMdd-xxx`（未自动生成，前端或导入时指定）
- 回款编号：`HK-yyyyMMdd-xxx`，查询当天已有数量 +1
- 工单编号：`WOyyyyMMddxxx`，查询当天已有数量 +1

## 七、开发顺序建议

1. **第一阶段**：crm-common + crm-system（用户/角色/菜单/部门/登录）→ 前后端登录打通
2. **第二阶段**：crm-customer（客户 CRUD + 跟进 + 标签 + 公海池）
3. **第三阶段**：crm-market（线索 + 渠道 + 分配）
4. **第四阶段**：crm-business（商机 + 合同 + 回款）
5. **第五阶段**：crm-service（工单 + 售后记录）
6. **第六阶段**：crm-report（看板 + 报表）
7. **第七阶段**：移动端适配 + 离线
8. **第八阶段**：操作手册 + UI 精修
